# Contributing Guidelines

We love contributions! We've compiled this documentation to help you understand our
contributing guidelines. [If you still have questions, please contact us](mailto:{{cookiecutter.contact_email}}) and
we'd be happy to help. 

## Getting started

If you are unfamiliar with git and GitHub, check out resources for getting started such as [this guide from GitHub](https://docs.github.com/en/get-started/onboarding/getting-started-with-your-github-account) or [this intro to git in VSCode](https://code.visualstudio.com/docs/sourcecontrol/intro-to-git).

If you work in Public Health Wales, you can skip step 1 and clone the repository itself. Other steps should be followed in the same way.

1. **Fork the repository:**
Start by forking this repository to your own GitHub account.

1. **Clone your fork:**
Clone the forked repository to your local machine.

1. **Set up your local copy of the package and repo:**
To work with the package locally, you can install an editable version of it (which
should also install its dependencies). As well as installing the package as editable,
contributors should also install the [pre-commit hooks](https://pre-commit.com/). To start
contributing, open your terminal and install the package and pre-commit hooks using:
    ```shell
    pip install -e .
    python -m pre_commit install
    ```

Pre-commit hooks are actions which are run automatically, typically
on each commit, to perform some common set of tasks.

Pre-commit hooks are a security feature to reduce (but not eliminate) 
the risk that certain secrets, large data files, and Jupyter notebook outputs are accidentally committed into the repository. The pre-commit hooks on this repo also help ensure code quality by running various linting checks and running the package's automated test suite.


1. **Check out a new branch for your changes:**
Always work on a new branch for your changes. This keeps things clean and organised.
    ```
    git checkout -b [branch-name] main
    ```

1. **Make your changes to the code:**
Make your changes to the code as you would normally. Run the code locally to check it works.

1. **Commit your changes**
Once you've made your changes, commit them:
    ```
    git add name_of_changed_file
    # Repeat git add if you've added multiple files
    git commit -m "Describe your changes"
    # A good convention for commit messages is to
    # finish the sentence "This change will [commit message]"
    # e.g. "Fix bug in error calculation"
    ```

1. **Push to your fork:**
Once you've made your changes, push them to your fork on GitHub.
    ```
    git push origin [branch-name]
    ```

1. **Open a pull request:**
Go to the main repository on GitHub, and you'll see a button to create a new pull request from your fork (or from your branch if you did not fork the repo). Provide a description of your changes. Link to relevant GitHub Issues from the backlog. Submit your pull request and request review from the maintainers. Please make sure to test your changes thoroughly before submitting a pull request. This ensures the integrity and quality of the project.

1. **Respond to changes:**
Address any requested changes on your branch, and obtain approval from the reviewers to merge.

1. **Merge main into your branch:**
Merge any changes on `main` into your branch. You can do this by navigating to your branch in the Command Prompt
and running:
    ```
    git fetch origin main
    git merge origin/main
    ```

1. **Increase the version number:**
This repo uses [bump-my-version](https://pypi.org/project/bump-my-version/) to manage versioning. The last commit before a PR is merged should
be a commit autogenerated by `bump-my-version`. Run `bump-my-version bump patch` (for back-compatible bug fixes), `bump-my-version bump minor` (for new features that are back-compatible) or `bump-my-version bump major` (for breaking changes/API changes etc) in the Command Prompt/Terminal (`bump-my-version` can also be replaced in the above by `python -m bumpversion`, although please ensure that its predecessors `bump2version` or `bumpversion` are not installed). This should be run and pushed
after the other changes on the branch are approved but before merge, so that the tagged and versioned commit represents the final extent of changes from the branch (including any amendments suggested by review). As well as pushing this last commit, check the name of the tag (e.g. v0.0.5; you can find it by running `git describe --tags --abbrev=0` in the Command Prompt) and push the tag `git push origin {TAG NAME}`. For more information on versioning, see [our notes](https://github.com/Public-Health-Wales/github-repo-guidance/wiki/How-to...-keep-track-of-code-version). 

1. **Merge your PR:**
Merge the PR using the button on GitHub.

## Testing

### Writing pytests

Aim to add tests when adding new functionality. 

[Tests use the `pytest` framework](https://pypi.org/project/pytest/
). Tests are stored in the `tests` folder. For pytest to find a test, all test files and tests must start with `test_` or finish with `_test.py`. 

## Running pytests

To run pytests in your terminal, run: 
```shell
pytest
```
in your root directory.
